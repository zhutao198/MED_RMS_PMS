### 3.1 Fail 用例详情

**Fail #1 — test_cross_module_e2e.py: req-decompose**
- 端点: POST /requirements/{id}/decompose
- HTTP=200, code=SY0101
- 错误信息: "URS只能拆解为PRS"
- 根因: 测试创建 URS 类型需求后尝试转为子需求，但按照业务规则 URS 只能拆解为 PRS，测试脚本未匹配这一规则。**不是 bug，是测试脚本问题。**

**Fail #2 — test_cross_module_e2e.py: baseline query**
- 端点: GET /baselines/{id}
- HTTP=200, code=SY0301
- 错误信息: "资源不存在"
- 根因: 跨模块测试中创建的 baseline id 与实际查询的 id 不一致（测试脚本路径问题）
- **状态: 测试脚本 bug，非后端 bug**

**Fail #3 — test_r150_trace_ipd_e2e.py: D4.1 audit_log 不应增长**
- 端点: POST /esignature/sign (同 user 双签被拒)
- 错误: 双签被拒后 audit_log 从 143 增长到 147（期望不变）
- 根因: 被拒绝的签名操作仍然写入了 audit_log（可能是在过滤器/拦截器层面记录的）
- **状态: 审计日志写入逻辑需复查** — 合规拒绝的操作是否应被记录取决于业务需求，但测试期望"不记录"。

## 四、哈希链完整性

| 指标 | 值 |
|------|-----|
| audit_log 总数 | 194 条 |
| 哈希链是否有效 | **false** |
| 最早断裂点 ID | 29 |
| 断裂类型 | PREV_HASH_MISMATCH |
| 最后有效 ID | 28 |

**断裂详情 (id=28,29):**
- id=28 (USER, operator=1): prev_hash=X, current_hash=A
- id=29 (USER, operator=5): prev_hash=X, current_hash=B
  - 第 29 条的 prev_hash 应为 A（等于第 28 条的 current_hash），但实际指向 X（与第 28 条相同的 prev_hash）
  - **根因**: 哈希链重建脚本存在逻辑问题，导致并行插入时多行指向同一个 prev_hash

**影响**: 哈希链在 id=29 处断裂，之后所有记录的哈希链验证都不可信。但 id≥29 内部自身链是连续的（id 29→30→31→32 各条自己的 prev_hash=上一条 current_hash）。
