### 1.1 关键发现

1. **架构骨架完整，合规闭环有缺口**：后端 325 端点覆盖了 PRD 全部 8 个模块，但 21 CFR Part 11 / IEC 62304 闭环有多处薄弱环节
2. **前端覆盖约 51%**：PRD 期望 75+ 原型页，前端实现 90 路由但部分为核心 CRUD 页面，缺少审计/合规专用操作页
3. **RBAC 后端已就绪，前端完全缺失**：63 权限码 + PermissionEnforceFilter 后端完善，但前端无路由守卫/无动态菜单/无按钮级指令
4. **PRD P0 全部可访问**，但部分功能强度不够（如状态机无转换表、领域事件退化同步）

## 七、跨域系统性问题

### 7.1 🔴 前端 RBAC 完全缺失

| 问题 | PRD 要求 | 当前状态 |
|------|---------|---------|
| 路由守卫 | 未登录跳转登录页 | ❌ **无**：静态路由全部可访问 |
| 动态菜单 | 按角色显示菜单项 | ❌ **全部硬编码**：所有用户看到全部 20+ 菜单 |
| 按钮级权限 | 无权限按钮隐藏/禁用 | ❌ **无 v-permission 指令** |
| 角色标识 | 从 JWT claims 获取 | ❌ **从 username 硬编码映射** |

**影响**：后端 RBAC 虽然拦截越权 API 调用，但用户可以看到所有菜单和页面（即使实际无法操作），体验差且易混淆。

### 7.2 🟡 领域事件机制退化

| PRD 期望 | 实际 |
|---------|------|
| 上游变更→自动标记下游 suspect | 需手动触发 assessImpact |
| 追溯断裂实时检测→仪表盘警告 | 需手动打开缺口页面 |
| 评审完成→自动通知相关人 | 站内通知 API 有但触发机制存疑 |
| 合规校验→自动拦截非法状态迁移 | 后端 if-else 判断，无正式状态转换表 |

**根因**：in-process Outbox 模式虽有，但订阅者注册不完整，事件触发点有缺口。

### 7.3 🟡 电子签名合规强度

| PRD 要求 | 实际 | 差距 |
|---------|------|------|
| RSA-Sign(signerId+meaning+timestamp+entityType+entityId+entityHash) | SHA-256(...) | 🔴 签名算法不同 |
| 二次认证（密码+OTP） | OTP + 密码已实现 | ✅ 一致 |
| 签名值验证 | verifySignature 端点 | ✅ 有 |
| 签署显现（11.50） | 签名记录含含义+时间戳 | ⚠️ 需确认 UI 上签名含义与记录是否不可分离显示 |

### 7.4 🟢 审计日志哈希链

- R157 已修复：valid=true，23 条哈希链校验通过
- 7 字段算法已对齐（SecurityUtils.calculateAuditHash 统一入口）
- **但 DB 触发器阻止 UPDATE/DELETE 尚未确认**

## 八、PRD 合规指标 vs 实现可度量性

| 指标 | PRD 目标值 | 当前系统能否自动度量 |
