## 📊 详细核实记录

### F1 哈希链断裂（确认 + 更严重）

**opencode 报告**：id=29 处 PREV_HASH_MISMATCH

**实测 SQL**：
```sql
SELECT id, prev_hash = LAG(current_hash) OVER (ORDER BY id) AS prev_match
FROM compliance_schema.t_audit_log WHERE id BETWEEN 27 AND 33;
```
**结果**：
| id | prev_match |
|----|------------|
| 27 | (起始) |
| 28 | ✅ t |
| **29** | **❌ f** |
| 30 | ✅ t |
| 31 | ✅ t |
| **32** | **❌ f** |
| 33 | ✅ t |

**根因（推断）**：
- id=29 prev_hash = `41ab2082ba40`（= id=27 的 prev），不是 id=28 的 current
- id=32 prev_hash = `4ae9fd90ffef`（= id=30 的 prev），不是 id=31 的 current
- 多个 LOGIN 事件（USER entity_type）并行写入时，prev_hash 计算用了同一时间点的快照
- **R147 已修复部分但没根除**：R147 rebuild 后仍有断链

**严重度**：**P0**（合规硬伤，21 CFR Part 11 §11.10(e) 要求完整可验证哈希链）

**修复建议**：检查 AuditLogService.recordAuditLog 的 prev_hash 查询 + 新 audit 写入是否在单一事务内完成（应 REQUIRES_NEW + 序列化）。

### F2 pd 用户登录失败（确认）

**opencode 报告**：pd 登录返回 SY0201

**实测 SQL**：
```sql
SELECT id, username, real_name, status FROM sys_schema.t_user WHERE username='pd';
```
**结果**：0 行（pd 用户**完全不存在**）

**实测 curl**：`POST /api/auth/login` 返回 `code=SY0201, msg=用户名或密码错误`

**根因**：
- 测试账号清单（CLAUDE.md）中声称有 9 角色（admin/qa_mgr/pm/re/reviewer/risk_mgr/compliance/viewer/pd）
- 实际 sys_schema.t_user 只有 8 角色（缺 pd）
- CLAUDE.md 与 DB 实际状态不一致（**文档漂移**）

**严重度**：**P0**（文档与代码不一致，且声称测试账号无法登录）

**修复建议**：要么补 pd 用户的种子数据，要么修正 CLAUDE.md 移除 pd 角色描述。

### F4 reviewer 缺 /baselines 权限（确认）

**opencode 报告**：reviewer 403 拒绝访问 /baselines

**实测 9 角色**：
| 角色 | GET /baselines/project/100 |
|------|---------------------------|
| admin | 200 ✅ |
| qa_mgr | 200 ✅ |
| re | 200 ✅ |
| **reviewer** | **403 ❌** |
| risk_mgr | 200 ✅ |
| compliance | 200 ✅ |
| viewer | 200 ✅ |
| pm | 200 ✅ |

**根因**：reviewer 角色在 t_role_permission 表中**未授权** BASELINE 相关权限
- 推测：baseline:view 权限没分给 reviewer
- 但所有非 admin 角色应能查看基线（合规审计场景需要）

**严重度**：**P1**

**修复建议**：t_role_permission 表补 `reviewer + baseline:view`，或确认角色设计是否合理。

### F6 /traceability/gaps/ignored SY0000（确认）

**opencode 报告**：HTTP=200, code=SY0000

**实测**：
```
{"code":"SY0000","data":null,"message":"系统异常，请稍后重试","timestamp":...}
```

**根因**：后端某个环节抛异常被 GlobalExceptionHandler 兜底返回 SY0000（system error 通用码）
- 可能原因：业务逻辑错误、SQL 异常、参数解析失败

**严重度**：**P2**

**修复建议**：查后端 logs（C:/temp/medrms-8080-r133-*.log）找对应请求的异常堆栈。

### F7 /projects 延迟 697ms（确认）

**opencode 报告**：GET /projects 延迟 697ms

**实测**：刚才 POST /projects 创建后 GET /projects 响应较慢

**根因（推断）**：
- 项目表未加合适的索引
- 项目列表查询缺分页限制（一次性拉所有项目）
- 关联查询 N+1（每个项目加载成员/任务等）

**严重度**：**P2**（性能问题，影响用户体验）

**修复建议**：profile SQL + 加索引 + 分页。

---

### F8 合规拒绝的签名写 audit_log（确认）

**opencode 报告**：双签被拒后 audit_log 从 143 增长到 147

**实测**：最近 1 小时 audit_log 有 10 条 `event_type=NULL` 记录

**根因（推断）**：
- R155/R156 加的 @AuditLog 注解用 around 包裹（先 business 再 audit_log）
- 即使 business 因 SG0102/SG0104 抛异常，audit_log 仍被写入（事务可能回滚？但 audit_log 表有记录）
- event_type=NULL 表明 audit_log 表的写入路径没有分类（可能是 sign 失败前的部分写入？）

**严重度**：**P2**（语义问题，可能影响合规审计解读）

**修复建议**：明确"业务失败时是否写 audit_log"业务规则（建议：失败也要写，但 event_type=REJECTED 分类）。
