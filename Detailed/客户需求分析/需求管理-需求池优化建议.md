## 二、每项变更的详细方案

### 2.1 新增"提出人"字段（P0）

**客户要求**: 增加提出人字段，优先通讯录同步，可文本输入，必填。

**方案**:

```
DB: req_schema.t_requirement_pool
  ADD COLUMN proposer VARCHAR(100) NOT NULL DEFAULT ''

后端: RequirementPool.java
  private String proposer;  // 新增字段

  AddToPoolRequest.java
  @NotBlank private String proposer;  // 必填校验

  RequirementPoolService.addToPool()
  新增 proposer 参数 → setProposer()
  
  GET /requirement-pool 响应
  返回 proposer 字段

前端: RequirementPool.vue 新增弹窗
  提出人: <el-input v-model="form.proposer" />
  提示：优先通讯录同步，可文本输入（通讯录功能待完善）
```

**影响范围**: 3 层（DB + 后端 + 前端），无副作用。

**通讯录说明**: 当前用户管理模块已有 `/api/users/search` 基础能力，但"通讯录"功能尚未产品化。建议：
- 一期：纯文本输入 + 必填校验
- 二期：配合用户管理完善后增加 autocomplete 下拉

---

### 2.2 ID 序列 3 位→4 位（P0）

**客户要求**: 日期+4 位序列，如 `202607160001`。

**当前**: `PoolIdGenerator` 使用 `String.format("%s%03d", datePart, seq)` → `20260716001`

**改动**: 后端 `%03d` → `%04d`

```java
// 改动前
String id = datePart + String.format("%03d", seq);
// 改动后
String id = datePart + String.format("%04d", seq);
```

**注意**: 已有数据的 ID 格式为 3 位序列（如 `20260713001`），新数据将变为 4 位（如 `202607170001`），两者共存不影响查询和排序。无需迁移历史数据。

---

### 2.3 增强查询条件（P0）

**客户要求**: 增加创建时间范围、标题/需求描述/ID/提出人模糊查询。

**后端改动**:

```java
// GET /requirement-pool 新增参数
@RequestParam(required = false) @DateTimeFormat(pattern = "yyyy-MM-dd") LocalDate createdAtStart,
@RequestParam(required = false) @DateTimeFormat(pattern = "yyyy-MM-dd") LocalDate createdAtEnd,
@RequestParam(required = false) String keyword  // 模糊匹配 title/rawDescription/id/proposer

// Service 层 LambdaQueryWrapper 增加条件
wrapper.between(createdAtStart != null, RequirementPool::getCreatedAt, createdAtStart, createdAtEnd)
       .and(keyword != null, w -> w
           .like(RequirementPool::getTitle, keyword)
           .or().like(RequirementPool::getRawDescription, keyword)
           .or().like(RequirementPool::getId, keyword)
           .or().like(RequirementPool::getProposer, keyword)
       )
```

**前端改动**:

```
新增筛选栏：
  [创建时间: 开始日期] ── [结束日期]
  [搜索框: 标题/描述/ID/提出人]
  保留原有：状态下拉 + 来源下拉
```

**安全**: `keyword` 参数需做 SQL 注入防护（MyBatis-Plus 的 `like` 使用预编译，天然免疫）。

### 2.8 表单草稿保存（P1）

**客户要求**: 取消按钮时保存上次未保存的信息，防止误操作丢失。

**方案**:

```javascript
// 打开新增弹窗时
onMounted(() => {
  const draft = sessionStorage.getItem('poolAddDraft')
  if (draft) form.value = JSON.parse(draft)
})

// 表单数据变化时自动保存
watch(form, (val) => {
  sessionStorage.setItem('poolAddDraft', JSON.stringify(val))
}, { deep: true })

// 提交成功后清除
function submitAdd() {
  // ... 提交逻辑
  sessionStorage.removeItem('poolAddDraft')
}
```

**选择 `sessionStorage` 而非 `localStorage`**: 关闭浏览器标签页后自动清理，避免残留数据。

## 三、需要客户确认的 3 个问题

### 问题 1：产品总监 / 总工角色映射

**背景**: 当前 RBAC 模型有 9 个角色，其中与需求管理相关的是 `re`（需求工程师）和 `pd`（产品经理）。系统中不存在"产品总监"和"总工"角色。

**请选择方案**：

| 方案 | 描述 | 影响 |
|-----|------|------|
| **A: 映射到现有角色** | 产品总监 → `pd`（产品经理），总工 → `pm`（项目经理） | 零改动，当天生效 |
| **B: 新增角色** | 新增 `PD_DIRECTOR`（产品总监）和 `CHIEF_ENGINEER`（总工），配置与 `pd`/`pm` 相同的 `req:*` 权限 | 需修改 RBAC 矩阵 + 权限配置 + 用户管理，约 1 天 |

**建议**: 如果这两个角色仅需"查看需求池"的权限，**方案 A** 足够。如果未来有独立权限诉求（如总工可以审批但不可以编辑），则选方案 B。

---

### 问题 2：OA 自动导入的技术实现方式

**背景**: OA 自动导入需要 OA 系统配合。目前有两种实现方式：

| 方式 | 描述 | OA 侧要求 | 我方改动 |
|-----|------|----------|---------|
| **A: REST 回调接口** | 我方提供 `POST /requirement-pool/oa-import` 接口，OA 系统在流程结束时调用 | OA 能发起 HTTP 请求 | 新增接口 + API Key 认证，约 1 天 |
| **B: 定时轮询** | 我方定时拉取 OA 导出的文件（CSV/JSON） | OA 能定时导出文件到指定位置 | 需额外基础设施（SFTP/共享目录），约 2 天 |
| **C: 半自动** | OA 负责人手动导出文件 → 人工导入（复用现有 `/import` 端点） | 人工操作 | 零改动，立即可用 |

**建议**: 一期用 **C（半自动）** 快速满足，复用现有导入功能；二期看 OA 对接成熟度再选 A 或 B。

---

### 问题 3：权限管控的时机

**客户原文**: "增加需求池的权限管理，需求工程师、产品经理、产品总监、总工，待完善用户管理功能后增加。"

**需要确认**：

1. "待完善用户管理功能后增加" 是指 **当前先不做严格权限控制**，仅靠前端菜单可见性？
2. 还是指 **用户的角色需要在用户管理页面可配置**，等配置功能完善后再启用权限校验？

**建议**：
- 当前：前端用 `v-permission` 指令控制菜单可见性（`['re', 'pd']` 可见，已有基础设施支持）
- 未来：用户管理完善后，后端 `PermissionMatrix.java` 增加精确路径规则（如 `POST /requirement-pool` 仅 `re/pd/PD_DIRECTOR/CHIEF_ENGINEER` 可访问）
