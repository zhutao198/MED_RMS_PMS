# 变更管理模块 — PRD 偏差与行业竞品对比分析报告

> **报告版本**: v1.0 | **编制日期**: 2026-07-17
> **对比基准**: 详细设计 v1.3 + 交互原型 v1.5 + IEC 62304:2016 + 21 CFR Part 11
> **行业对标**: Polarion (Siemens)、Jama Connect、Codebeamer (PTC)、Helix ALM (Perforce)
> **结论概要**: 6 大类、24 项偏差（BLOCKER 2 / MAJOR 7 / MINOR 10 / TRIVIAL 5）

---

## 一、评估方法论

### 1.1 评估维度

| 维度 | 权重 | 说明 |
|------|------|------|
| 功能完整性 | 40% | 是否覆盖 PRD / 详细设计 / 原型定义的全部功能 |
| 合规合规性 | 30% | 是否满足 IEC 62304 §5/§7/§8、21 CFR Part 11、ISO 13485 §7.3 |
| 可用性 | 15% | 交互是否直观、信息密度是否合理 |
| 行业对标 | 15% | 与主流 ALM 工具的功能差距 |

### 1.2 评估范围

| 模块 | 范围 | 评估文件 |
|------|------|----------|
| 后端 | API 端点 + 业务逻辑 + 权限 | med-rms-change (22 endpoints) |
| 前端 | 7 个 Vue 页面 + 路由 + 菜单 | changes/*.vue (7 文件) |
| 数据库 | 6 张表 + DDL | t_change_request + 5 子表 |

## 三、与 PRD / 详细设计的偏差详解

### 类别 A：功能缺失（BLOCKER/MAJOR）

#### A1 🔴 BLOCKER：变更执行缺少证据持久化

| 项目 | 描述 |
|------|------|
| **详细设计要求** | 执行变更时需创建需求新版本、记录 ChangeExecution 快照（§4.3 executeChange 伪代码）；原型 change-execute 要求"执行检验单 + 附件" |
| **当前实现** | ChangeExecute.vue 有执行清单 + 进度条，但**无证据上传功能**，每项执行无"备注"文本输入，无"实际完成日期"字段，无执行人签名 |
| **后端差距** | `executeChange()` 已实现需求版本快照，但 accept body 仅为 `updatedRequirement`，无执行证据字段 |
| **影响** | QA 执行无据可查，违反 21 CFR Part 11 §11.10(e) 审计追踪要求 |
| **行业对标** | Polarion: 每项执行变更可附加工作证明（截图/日志/审批单），版本快照自动生成 |

#### A2 🟠 MAJOR：验证清单硬编码，不从后端动态加载

| 项目 | 描述 |
|------|------|
| **当前实现** | ChangeVerify.vue 中 5 项验证项全部硬编码在 `verifyItems` 数组中 |
| **问题** | 不可配置/扩展，不同项目/变更类型的验证项应不同；证据上传仅前端暂存（`auto-upload=false`），未真正上传到服务器 |
| **后端差距** | 无验证项配置端点、无证据文件持久化端点 |
| **影响** | 验证流程固化，扩展需改前端代码 |
| **行业对标** | Codebeamer: 验证项模板化，可按变更类型自动生成 |

#### A3 🟠 MAJOR：审批统计卡数据为空

| 项目 | 描述 |
|------|------|
| **当前实现** | ChangeApprovals.vue 显示 4 个统计卡（待审批/今日已审/本周已审/平均时长），但**待审批数直接等于前端数组长度**，其余 3 个统计值全部**硬编码为 0** |
| **后端差距** | 无审批统计专用端点（预计需要 `GET /changes/approvals/stats?userId=N`）|
| **影响** | 统计功能形同虚设，用户无法获取实际工作负载信息 |
| **行业对标** | Jama: 审批工作台实时统计，含"待我审批/已过期/本月完成/平均响应时长" |

#### A4 🟠 MAJOR：优先级字段体系不统一

| 项目 | 描述 |
|------|------|
| **PRD 要求** | 变更类型 × 审批策略矩阵（§6）定义 4 类优先级：MAJOR(双签) / NORMAL(单签) / DOCUMENT(单签) / EMERGENCY(事后补) |
| **原型要求** | `changes` 原型要求独立"优先级"列（MAJOR/NORMAL/DOCUMENT/EMERGENCY 徽标）；`change-edit` 原型要求 MUST/SHOULD/COULD 三档 |
| **当前实现** | ChangeList 展示 `urgency`（NORMAL/URGENT）无优先级列；ChangeCreate 表单无优先级选择器；后端 ChangeRequest 实体有 `riskLevel` 字段但前端未利用 |
| **影响** | 审批策略矩阵的前端条件依赖模糊，用户无法直观判断变更的审批要求 |

#### A5 🟠 MAJOR：影响范围字段不完整

| 项目 | 描述 |
|------|------|
| **原型要求** | 影响范围下拉：单系统 / 多系统 / 跨模块；影响范围 % 进度条（low绿/medium黄/high红） |
| **当前实现** | ChangeCreate 表单无"影响范围"输入；ChangeList 仅展示 URS/PRS/SRS 三标签（缺 DRS/TC），无百分比进度条 |
| **后端差距** | `ChangeRequest.affectedItems` 字段（TEXT）已存在但前端未用；影响分析结果虽有等级但未汇总为 % |
| **影响** | 列表页无法直观判断变更影响大小 |

#### A6 🟠 MAJOR：影响分析维度与原型定义不一致

| 项目 | 描述 |
|------|------|
| **原型要求** | 分析选项卡片：需求 / 追溯链 / 风险 / 测试用例；分析方向（仅下游/双向/仅上游）；分析深度（一级/二级/全链路） |
| **当前实现** | ChangeImpactAnalysis.vue 的 4 个选项为：需求追溯 / 测试用例 / 基线影响 / SOUP 组件——**与原型定义完全不同**；无分析方向/深度配置；无"提交影响评估报告"按钮 |
| **后端差距** | `performImpactAssessment()` 自动分析追溯链 + 标记 suspect，但无方向/深度参数控制 |
| **影响** | 影响分析维度与原型/设计不一致，需业务确认对错 |

#### A7 🟠 MAJOR：委派功能缺用户选择器

| 项目 | 描述 |
|------|------|
| **当前实现** | 委派对话框仅支持**输入用户 ID**（`el-input-number`），需手动输入数字 |
| **原型/行业要求** | 应支持用户搜索/选择器（`el-select filterable`），R110 已在变更委派中修复此问题 |
| **影响** | 用户需记忆他人 ID，易出错 |

### 类别 B：合规差距（MAJOR/MINOR）

#### B1 🟠 MAJOR：审批流程缺少 21 CFR Part 11 电子签名 UI 引导

| 项目 | 描述 |
|------|------|
| **PRD 要求** | 审批操作必须伴随电子签名（21 CFR Part 11 §11.100），且需展示签名含义说明 |
| **当前实现** | ChangeApprovals.vue 中"批准"按钮调用 `ESignPopup`，但**无签名含义说明文案**（如"根据 21 CFR Part 11，您的电子签名将成为本审批的法定签名"）|
| **原型要求** | change-approve 原型要求：审批意见（必填）+ Part 11 提示 + "批准并签署"按钮 |
| **影响** | 合规提示不充分，用户可能未意识到电子签名的法律效力 |

#### B2 🟡 MINOR：变更执行无电子签名

| 项目 | 描述 |
|------|------|
| **PRD 要求** | IEC 62304 §5.5.4 要求执行变更也需受控签名 |
| **当前实现** | `executeChange()` 无签名校验，仅检查状态为 APPROVED |
| **后端差距** | `executeChange()` 缺少 `signatureId` 参数和签名验证 |
| **行业对标** | Polarion/Codebeamer: 执行变更同样需要电子签名（二次确认） |

#### B3 🟡 MINOR：紧急变更事后补审批无时限控制

| 项目 | 描述 |
|------|------|
| **PRD 要求** | EMERGENCY 变更事后补审批（§6 审批策略矩阵），但未规定补审批时限 |
| **行业标准** | ISO 13485 §7.3.8 要求异常变更应在**合理期限内**完成补审批 |
| **当前实现** | `emergencyDirectExecute()` 无超时提醒或补审批截止日期 |
| **行业对标** | Codebeamer: 紧急变更生成补审批任务，设定截止日期（默认 7 天） |

### 类别 C：UI/UX 差距（MINOR）

#### C1 🟡 MINOR：列表缺少标题列、申请人列、优先级筛选

| 项目 | 描述 |
|------|------|
| **原型要求** | changes 列表 8 列（编号/标题/优先级/状态/类型/影响范围/申请人/日期）+ 状态/优先级/关键字三合一筛选 |
| **当前实现** | ChangeList 无独立"标题"列（与原因混合）、无"申请人"列（仅存 requestBy ID）、无"优先级"列（仅展示 urgency）；筛选仅"状态 + 需求编号"，缺优先级/关键字 |
| **影响** | 列表信息密度低于原型，缺少常用筛选维度 |

#### C2 🟡 MINOR：ChangeCreate 无流程步骤条

| 项目 | 描述 |
|------|------|
| **原型要求** | 新建页面底部应有 5 步流程可视化条（提交→影响评估→审批→执行→验证→关闭） |
| **当前实现** | ChangeCreate.vue 底部用 `<ol>` 文字列出 5 步，**非可视化步骤条** |
| **影响** | 用户难以直观了解变更生命周期 |
| **行业对标** | Polarion: 新建流程展示水平步骤条，当前处于第几步高亮 |

#### C3 🟡 MINOR：状态机枚举前端不一致

| 项目 | 描述 |
|------|------|
| **当前实现** | ChangeList 状态枚举：DRAFT/ANALYZING/PENDING_APPROVAL/APPROVED/EXECUTING/VERIFIED/CLOSED；ChangeRequest 状态枚举：DRAFT/PENDING_ANALYSIS/PENDING_APPROVAL/APPROVED/REJECTED/IN_PROGRESS/COMPLETED |
| **问题** | 两个文件的状态名不一致（ANALYZING vs PENDING_ANALYSIS，EXECUTING vs IN_PROGRESS，VERIFIED vs COMPLETED），与后端 10 状态定义也有差异 |
| **影响** | 后端状态可能在前端无对应样式/标签，导致显示异常 |

### 类别 D：行业对标差距

#### D1 🟡 MINOR：无变更请求模板

| 项目 | 描述 |
|------|------|
| **行业标准** | Polarion/Codebeamer/Jama: 支持变更请求模板（按变更类型预设字段/审批流/验证项） |
| **当前实现** | ChangeCreate 表单固定字段集，不可按类型定制 |
| **建议** | 低优先级，可等需求池模板化功能统一支持 |

#### D2 🟡 MINOR：无变更影响热力图

| 项目 | 描述 |
|------|------|
| **行业标准** | Jama: 变更影响的追溯链路用热力图可视化（红色=高影响，黄色=中，绿色=低）；Polarion: 追溯矩阵用图标标记影响等级 |
| **当前实现** | ChangeImpactAnalysis.vue 仅统计卡 + 影响项表格，无追溯链路可视化 |
| **建议** | 中期优化项，可结合 trace-graph 图谱实现 |

#### D3 🟢 TRIVIAL：无关联变更推荐

| 项目 | 描述 |
|------|------|
| **行业标准** | Codebeamer: 根据变更需求的追溯链路，自动推荐"可能也需变更"的关联项 |
| **当前实现** | 影响分析的 `markSuspectTraces` 已标记 suspect 追溯链接，但前端未提示用户跳转查看 |
| **建议** | 在 ChangeRequest 详情页增加"关联变更"区块（已有相关变更列表但无推荐逻辑） |

#### D4 🟢 TRIVIAL：无变更日历/时间线视图

| 项目 | 描述 |
|------|------|
| **行业标准** | Helix ALM: 甘特图展示变更执行计划；Polarion: 日历视图展示变更里程碑 |
| **当前实现** | 仅 `GET /changes/{id}/timeline` 返回事件列表，无可视化时间线 |
| **建议** | 低优先级，可结合项目甘特图统一实现 |
